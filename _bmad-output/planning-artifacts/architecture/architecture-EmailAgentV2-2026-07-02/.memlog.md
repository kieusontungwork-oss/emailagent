- (decision) State Ownership: The system follows the 'Pure Orchestrator' paradigm. Postgres is the single source of truth for both domain data and operational state (request_logs for idempotency). Binds: Idempotency checks and audit logs must query Postgres, not Redis. Prevents: State fragmentation across datastores and loss of processing history if Redis is flushed.
- (decision) Pipeline Structure: The n8n architecture follows the 'Modular Sub-workflows' pattern. A central Controller workflow delegates tasks (Data Prep, AI Extraction, Database/Report) to isolated sub-workflows, and routes all errors to a universal Mailroom/Error-Handler sub-workflow. Binds: Workflows must be built as small, independently testable units. Prevents: Monolithic workflow spaghetti and inability to test components in isolation.
- (decision) Code Lifecycle: Workflows are managed via Git-Backed CI/CD (Infrastructure as Code). n8n workflow JSON files must be committed to source control, and deployment to the air-gapped production subnet is handled via an automated pipeline. Binds: No manual UI-driven edits in production. Prevents: Unaudited changes, configuration drift, and inability to rollback.

- (decision) Custom Containerization: n8n runs in a custom, extended Docker container. Binds: The deployment environment must build a custom n8n image embedding CLI tools (pdftk, Python, markitdown) and explicitly allow Execute Command node execution. Prevents: Unmet dependencies for local CLI-driven workflow execution and security blocks.
